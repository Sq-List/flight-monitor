# macOS 本地机票采集设计

## 目标

使用当前 Mac 已验证可用的家庭网络和可见 Chromium 采集携程报价。Mac 不需要持续开机；处于已登录、联网状态时按计划运行，错过计划时间后在下次唤醒或登录时补跑。

## 现状证据

同一查询地址已经完成四组对照验证：

- 当前 Mac、无头 Chromium：返回 `whaleguard block`。
- 当前 Mac、可见 Chromium：读取到 9 张航班卡片，最低往返总价为 ¥3538。
- GitHub 托管运行器、无头 Chromium：返回 `whaleguard block`。
- GitHub 托管运行器、Xvfb 可见 Chromium：仍返回 `whaleguard block`。

因此采集成功同时依赖当前 Mac 的网络环境和可见浏览器，继续调整 GitHub 托管运行器没有依据。

现有电脑使用记录只有约两天，较稳定的活跃窗口为 10:20–12:10 和 14:00–16:10，傍晚也有使用记录。时间安排基于这些已观察窗口，并用唤醒补跑消除样本不足带来的影响。

## 运行方式

使用当前用户的 macOS `LaunchAgent`，不安装 GitHub 自托管运行器：

- 用户登录时尝试运行一次。
- 每天 10:30、14:30、18:30 尝试运行。
- Mac 在计划时间睡眠时，`StartCalendarInterval` 会在下次唤醒后合并为一次补跑。
- 最近一次采集距当前不足两小时时跳过，避免登录与固定时间相邻造成重复查询。
- 采集时设置 `FLIGHT_MONITOR_HEADLESS=false`，允许 Chromium 窗口短暂出现。

`LaunchAgent` 运行在当前用户的图形会话中，因为后台系统服务无法可靠提供可见 Chromium 所需的桌面环境。

## 运行目录与数据发布

定时任务使用独立运行目录，不直接在当前开发目录中执行，避免自动拉取、提交与用户未提交改动相互影响。运行目录保存仓库副本、Node.js 依赖和 Playwright Chromium。

每次实际采集按以下顺序执行：

1. 快进同步远端 `main`。
2. 检查 `data/latest.json`；不足两小时则正常结束。
3. 以可见 Chromium 执行现有采集器。
4. 无论采集成功或失败，都保存 `data/latest.json`、`data/history.json` 和现有失败附件。
5. 数据发生变化时，只提交两个 JSON 数据文件并推送到 `main`。

首次部署前，先把当前开发目录中的 Mac A/B 历史与远端云端历史按 `checked_at` 合并去重。所有唯一历史记录都保留，`latest.json` 取时间最新的一次结果；不得用任何一侧整体覆盖另一侧。

## 失败处理

- 页面被风控时沿用现有 `captcha` 状态和诊断附件，不伪造报价。
- 网络或 GitHub 推送失败时保留本地结果；下次运行先重试同步和发布。
- 单次失败不立即高频重试，下一计划时间或下次登录再运行。
- 日志写入用户日志目录，便于判断任务是否启动、跳过、采集或推送失败。

## 验证

1. 单元测试覆盖两小时去重判断和运行结果处理。
2. 校验 `LaunchAgent` 配置能被 macOS 正确解析。
3. 保持当前开发目录的两个未提交数据文件不丢失，完成本地与远端历史合并对账。
4. 安装后手动触发一次本地任务，要求可见 Chromium 成功取得航班卡片和正数报价。
5. 验证 GitHub 上的 `latest.json`、`history.json` 已更新，且历史条数与合并结果一致。
6. 验证两小时内再次触发会跳过，不产生新历史记录和提交。

## 边界与关键假设

- 不要求 Mac 保持开机，不主动唤醒或阻止睡眠。
- 不接入登录态、Cookie、代理或反检测补丁。
- 不点击选择返程；价格仍是“选择去程”页面显示的往返总价。
- 不增加通知渠道；本次只负责稳定采集并发布 JSON。
- 关键假设是当前 Mac 网络与可见 Chromium 能持续通过携程风控。若该条件失效，调整运行时间不能解决采集问题。
